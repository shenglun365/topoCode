# TopoOne 系统资源需求分析

> 基于各组件官方文档与社区实测数据整理。

---

## 一、各组件资源需求明细

### 1. Electron App (基础运行时)

| 指标 | 数值 | 说明 |
|------|------|------|
| **磁盘空间 (安装)** | 150-250 MB | 生产构建包 (asar + native modules) |
| **磁盘空间 (开发)** | 500 MB - 1 GB | 含 node_modules、源码、构建缓存 |
| **RAM (空闲)** | 150-300 MB | 主进程 + 1 个渲染进程 |
| **RAM (活跃)** | 400-800 MB | 多窗口/多标签页场景 |
| **RAM (含 Monaco Editor)** | +100-200 MB | 大文件编辑时额外开销 |
| **CPU** | 单核即可启动 | 推荐双核以上 |
| **GPU** | 可选 (硬件加速) | Chromium 默认启用 GPU 渲染 |

**说明**: Electron 每个窗口/标签页都会创建一个独立的 Chromium 渲染进程，每个进程约 100-200 MB。TopoOne 的 UI Shell 架构 (活动栏 + 多面板) 通常只需 1-2 个渲染进程。

| **CPU** | 单核可运行 | 推荐双核 (解析任务并行) |
| **GPU** | 不需要 | |

**依赖包磁盘占用参考**:
- `fastapi` + `uvicorn`: ~10 MB

- `celery` + `redis` (broker): ~30 MB
- `chromadb`: ~50 MB
- `networkx`: ~15 MB
- `pydantic`, `httpx`, `aiofiles`: ~20 MB

### 3. Tree-sitter (含 Python/Go/JS/Java 解析器)

| 指标 | 数值 | 说明 |
|------|------|------|
| **磁盘空间 (核心库)** | 5-10 MB | tree-sitter 运行时 + Python bindings |
| **磁盘空间 (每个语言解析器)** | 1-3 MB/语言 | 编译后的 WASM 或原生 so 文件 |
| **磁盘空间 (4 个语言总计)** | ~10 MB | Python + Go + JS + Java |
| **RAM (空闲)** | < 5 MB | 加载解析器后 |
| **RAM (解析大文件)** | 10-50 MB | 取决于文件大小与 AST 复杂度 |
| **CPU** | 单核即可 | 解析速度: ~1-5 MB/s (视语言复杂度) |
| **GPU** | 不需要 | |

**说明**: Tree-sitter 是增量解析器，首次解析后缓存 AST，后续增量更新极快。对于 10k 文件的项目，全量解析约需 10-30 秒 (单核)。

### 4. Ollama 运行时 + qwen2.5-coder:7b 模型

#### 4.1 Ollama 运行时

| 指标 | 数值 | 说明 |
|------|------|------|
| **磁盘空间 (Ollama 二进制)** | 50-100 MB | 含 llama.cpp 后端 |
| **磁盘空间 (模型缓存目录)** | 取决于下载的模型 | `~/.ollama/models/` |
| **RAM (Ollama 进程空闲)** | 50-100 MB | 无模型加载时 |
| **CPU** | 单核可运行 | 推荐多核 (推理加速) |
| **GPU** | 强烈推荐 (NVIDIA CUDA) | 无 GPU 时纯 CPU 推理极慢 |

#### 4.2 qwen2.5-coder:7b 各量化版本

| 量化版本 | 磁盘空间 | RAM (最低) | RAM (推荐) | GPU VRAM (最低) | GPU VRAM (推荐) | 推理速度 (CPU) | 推理速度 (GPU) |
|----------|----------|------------|------------|-----------------|-----------------|----------------|----------------|
| **Q4_K_M** (默认) | **4.7 GB** | 6 GB | 8 GB | 6 GB | 8 GB | ~2-5 tok/s | ~50-100 tok/s |
| **Q5_K_M** | **5.3 GB** | 7 GB | 8 GB | 7 GB | 8 GB | ~2-4 tok/s | ~45-90 tok/s |
| **Q8_0** | **6.9 GB** | 8 GB | 10 GB | 8 GB | 10 GB | ~1.5-3 tok/s | ~40-80 tok/s |
| **F16** (全精度) | **14 GB** | 16 GB | 20 GB | 14 GB | 16 GB | ~0.5-1 tok/s | ~30-60 tok/s |

**说明**:
- Q4_K_M 是 Ollama 的默认量化级别，在质量与资源间取得最佳平衡
- 7B 参数模型的理论最小内存 = 7B × 4 bits / 8 = 3.5 GB，加上 KV cache、上下文窗口、运行时开销，实际需 6+ GB
- CPU 推理速度取决于 CPU 型号 (上述数据基于 Intel i7 / AMD Ryzen 7 级别)
- GPU 推理速度取决于 GPU 型号 (上述数据基于 RTX 3060/4060 级别)
- 上下文窗口越大 (如 32k token)，KV cache 占用越多 RAM/VRAM

#### 4.3 GPU 要求详情

| GPU 级别 | VRAM | 能否运行 Q4_K_M | 推理体验 |
|----------|------|-----------------|----------|
| **RTX 3050 / 4050** | 6 GB | 勉强 (需关闭其他应用) | 可用但较慢 |
| **RTX 3060 / 4060** | 8-12 GB | 流畅 | 推荐入门级 |
| **RTX 3070 / 4070** | 8-12 GB | 流畅 | 推荐 |
| **RTX 3080 / 4080** | 10-16 GB | 非常流畅 | 可跑 Q8_0 |
| **RTX 4090** | 24 GB | 非常流畅 | 可跑 Q8_0 + 大上下文 |
| **Mac M1/M2/M3 (统一内存)** | 8-24 GB | 流畅 | 统一内存架构，速度介于 CPU/GPU 之间 |
| **无 GPU (纯 CPU)** | - | 可运行 | 极慢 (~2-5 tok/s)，仅适合开发测试 |

### 5. ChromaDB (本地向量数据库)

| 指标 | 数值 | 说明 |
|------|------|------|
| **磁盘空间 (安装)** | 30-50 MB | Python 包 + 依赖 |
| **磁盘空间 (运行时数据)** | 取决于向量数量 | 每个向量 ~128-4096 bytes (取决于维度) |
| **磁盘空间 (典型知识库)** | 100 MB - 2 GB | 10k-100k 文档片段 |
| **RAM (空闲)** | 50-100 MB | 嵌入式模式 |
| **RAM (活跃)** | 200-500 MB | 加载索引 + 查询 |
| **RAM (大规模)** | 1-2 GB | 百万级向量 |
| **CPU** | 单核可运行 | 推荐双核 (embedding 计算) |
| **GPU** | 不需要 | |

**说明**: ChromaDB 默认使用 HNSW 索引，内存占用与向量数量成正比。对于 TopoOne 的知识库场景 (数千至数万文档片段)，资源占用在可接受范围内。

### 6. SQLite (轻量级数据库)

| 指标 | 数值 | 说明 |

| **磁盘空间 (安装)** | 0 MB | Python 内置，无需额外安装 |
| **磁盘空间 (数据库文件)** | 取决于数据量 | 项目元数据: < 10 MB |
| **RAM (空闲)** | < 10 MB | 连接池空闲 |
| **RAM (活跃)** | 20-50 MB | 并发查询 + WAL 模式 |
| **CPU** | 单核即可 | 轻量级操作 |
| **GPU** | 不需要 | |

**说明**: SQLite 是 TopoOne 的主要本地存储方案 (项目元数据、知识库文档、配置、分析缓存)。单文件数据库，零配置，适合桌面应用。

### 7. Neo4j Community Edition (知识图谱 - 可选)

| 指标 | 数值 | 说明 |
|------|------|------|
| **磁盘空间 (安装)** | 200-300 MB | Java runtime + Neo4j 服务器 |
| **磁盘空间 (数据库)** | 取决于图规模 | 10k 节点: ~50 MB; 100k 节点: ~500 MB |
| **RAM (最低)** | 2 GB | Neo4j 官方最低要求 |
| **RAM (推荐)** | 4-8 GB | 生产级性能 |
| **RAM (大规模图)** | 8-16 GB | 百万级节点/边 |
| **CPU** | 双核最低 | 推荐四核以上 |
| **GPU** | 不需要 | |

**说明**: Neo4j 基于 JVM，启动时需分配堆内存 (默认 4GB)。对于 TopoOne 的知识图谱场景，如果节点数 < 10k，建议优先使用 NetworkX (内存中图)，仅在需要持久化大规模图时才引入 Neo4j。

| **含 AI 推理** (CPU) | 四核 | 八核 | CPU 推理速度关键 |

|------|------|------|
| **无 AI 功能** | 不需要 | Electron 硬件加速可选 |
| **AI 推理 (开发/测试)** | 不需要 (CPU 可用) | 速度较慢 (~2-5 tok/s) |

## 四、资源优化建议

1. **模型量化选择**: 优先使用 Q4_K_M (4.7 GB)，在质量与资源间取得最佳平衡。仅在需要更高精度时切换到 Q5_K_M 或 Q8_0。

2. **按需加载模型**: Ollama 支持 `ollama unload <model>` 释放 VRAM/RAM。TopoOne 可在 AI 助手非活跃时自动卸载模型。

3. **图谱存储策略**: 节点数 < 10k 时使用 NetworkX (内存中)，> 10k 时考虑 Neo4j。避免同时运行两者。

4. **Electron 内存优化**: 使用 `contextBridge` 减少渲染进程与主进程间的数据拷贝；大文件使用 `ipcRenderer.invoke` 异步加载。

5. **ChromaDB 持久化**: 启用持久化模式 (`persist_directory`)，避免每次启动重新构建向量索引。

6. **Celery Worker 数量**: 根据 CPU 核心数设置 worker 数量 (推荐 = CPU 核心数 - 1)，避免过度并行导致资源争用。

7. **Tree-sitter 增量解析**: 利用 tree-sitter 的增量解析能力，只重新解析变更文件，大幅降低 CPU 和 RAM 消耗。

## 五、启动顺序与资源分配

```
启动顺序:
1. Electron (主进程)          → 150-300 MB RAM
2. FastAPI + uvicorn          → +50 MB RAM
3. SQLite (嵌入式)            → +10 MB RAM
4. ChromaDB (嵌入式)          → +50-100 MB RAM
5. Ollama (后台服务)          → +50-100 MB RAM (无模型)
6. 模型加载 (按需)            → +6-8 GB RAM/VRAM
7. Neo4j (按需启动)           → +2-4 GB RAM
8. 外部 Agent (按需调用)      → +200-500 MB RAM (临时)

总计 (标准场景):
- 无 AI: ~500 MB RAM
- 含 AI (GPU): ~1-2 GB RAM + 6-8 GB VRAM
- 含 AI (CPU): ~8-10 GB RAM
```
