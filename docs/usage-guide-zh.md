## 1. 前置准备

### 1.1 确认后端运行

启动应用后，底部状态栏显示后端连接状态：

- 🟢 **已连接** — Python 后端运行正常
- 🔴 **未连接** — 请检查 Python 环境配置，参考 README 安装依赖
- ⏳ **连接中** — 等待后端启动（通常 3-10 秒）

如果状态长时间显示红色，请检查：

1. Python 3.10+ 是否正确安装
2. 依赖是否完整安装 (`pip install -r requirements.txt`)
3. 端口 5671/5680/3456 是否被占用

### 1.2 配置 LLM 模型

在 **设置 → 模型配置** 中添加模型（详见 README 的 LLM 配置章节）。架构分析建议使用本地模型以确保响应速度。

### 1.3 确保 Web 服务可用

浏览器访问 `http://localhost:3456`，确认 Web 文档服务正常响应。

## 2. 项目导入

> 截图: `docs/images/usage/zh/project-import.png`

### 操作步骤

1. 进入 **首页**（左侧导航栏第一个图标）
2. 点击 **导入项目** 按钮
3. 在弹出的对话框中选择项目的**本地源码目录**
4. 系统自动扫描目录结构并开始导入

> **💡 关于代码生成项目**：TopoCode 直接解析磁盘上的源码文件，不会自动执行构建或代码生成流程。部分项目包含代码生成步骤（如 protobuf、graphql-codegen、`go generate` 等），生成的源码不在原始代码目录中，直接导入不会包含这些文件。**如需更完整的分析**，可在导入前手动执行代码生成命令。请**按需选择**，不必强求覆盖全部生成代码。
>
> 常见代码生成命令示例：
>
> | 语言 | 典型代码生成场景 | 导入前可执行 |
> |---|---|---|
> | C / C++ | autoconf 生成 config.h / yacc / bison / flex / Qt MOC / protobuf | `./configure` / `bison -d parser.y` / `moc header.h` / `protoc --cpp_out=.` |
> | Go | stringer / mockgen / protobuf | `go generate ./...` / `protoc --go_out=.` |
> | TypeScript | graphql-codegen / protobuf-ts / openapi-generator | `npx graphql-codegen` / `protoc --ts_out=.` |
> | Dart | freezed / json_serializable / drift / protobuf | `dart run build_runner build` / `protoc --dart_out=.` |
> | Java | protobuf / Dagger / MapStruct 等注解处理器 | `protoc --java_out=.` |
> | Kotlin | protobuf / KSP | `protoc --kotlin_out=.` |
> | Swift | protobuf / Sourcery | `protoc --swift_out=.` / `sourcery --sources ...` |
> | C# | protobuf / T4 模板 | `protoc --csharp_out=.` |
> | Python | protobuf / Cython | `protoc --python_out=.` |
> | 其他语言 | protobuf / thrift / gRPC 等代码生成器 | 对应语言代码生成命令 |

### 导入过程

- 扫描文件类型、统计代码行数
- 构建文件树索引
- 识别项目主语言

导入进度在顶部全局遮罩层显示。大型项目（数万文件）可能需要 1-5 分钟。

### 成功标志

导入完成后，项目卡片出现在首页列表中，显示项目名称、文件数量和主语言。

### 失败处理

| 现象 | 原因 | 处理 |
|---|---|---|
| 导入按钮无响应 | 目录权限不足 | 尝试以管理员权限运行应用 |
| 导入进度卡住不动 | 文件过多或存在符号链接环 | 检查项目目录，排除 node_modules/.git 等目录 |
| 导入后文件数为 0 | 选择了空目录或不支持的源码类型 | 确认目录包含支持的编程语言文件 |
| 导入后提示"路径不存在" | 目录已被移动或删除 | 在项目卡片上点击"更新路径"或重新导入 |

## 3. 创建分析任务

> 截图: `docs/images/usage/zh/create-task.png`

导入项目后，在左侧文件树中点击项目节点，然后：

1. 点击 **分析** 标签页
2. 点击 **创建任务**
3. 填写任务信息：
   - **任务名称** — 给本次分析取一个名字
   - **分析类型** — 选择分析范围（全量解析 / 增量分析等）
   - **分析范围** — 可指定子目录（默认分析整个项目）
   - **文件过滤** — 可限定文件后缀和排除目录
4. 点击 **确定** 创建任务

### 任务状态说明

| 状态 | 含义 |
|---|---|
| `pending` | 等待执行 |
| `running` | 正在分析 |
| `done` | 分析完成 |
| `error` | 分析失败 |
| `cancelled` | 已取消 |

## 4. 代码解析 (AST)

> 截图: `docs/images/usage/zh/task-running.png`

创建任务后，在任务列表中找到该任务，点击 **运行**：

### 解析流程

1. **文件扫描** — 遍历项目文件树，识别所有源代码文件
2. **AST 解析** — 使用 Tree-sitter 对每个文件进行语法解析，提取：
   - 符号定义（函数、类、接口、变量等）
   - 引用关系（调用、继承、实现、导入等）
   - 文件间依赖
3. **图构建** — 将解析结果构建为符号图和依赖图
4. **社区发现** — 使用 Louvain/Leiden 算法将相关节点聚类为"社区"（即逻辑模块）

### 耗时预估

以下为**单并发、单次全量解析**的参考值。实际耗时受 CPU 性能、磁盘 I/O、项目语言（C/C++ 较慢）影响：

| 项目规模 | 文件数量 | AST 解析 | 图构建 + 社区发现 | 合计 |
|---|---|---|---|---|
| 小型 | < 500 | 1 - 5 分钟 | 30秒 - 2分钟 | 2 - 7 分钟 |
| 中型 | 500 - 5,000 | 10 - 30 分钟 | 2 - 10 分钟 | 15 - 40 分钟 |
| 大型 | 5,000 - 50,000 | 1 - 3 小时 | 10 - 30 分钟 | 1.5 - 4 小时 |
| 超大型 | > 50,000 | 3 - 8 小时 | 30 - 60 分钟 | 4 - 9 小时 |

> **注**：首次解析最慢，因为需要构建完整的索引数据库。解析完成后，后续的增量同步会快得多。C/C++ 项目因宏和模板展开较慢，Python/JS 项目通常更快。

### 截断执行

对于大型项目，可以将分析范围缩小到特定子目录，实现**截断执行**：

1. 创建任务时，在 **分析范围** 中指定子目录（如 `src/core/`）
2. 系统仅解析该目录及其依赖文件，跳过其他部分
3. 分析结果仅反映该子模块的架构

**再次执行时跳过已完成部分**：如果任务在分析过程中被中断（或您手动停止），**再次运行同一任务时，系统会自动跳过已完成的文件**，仅继续处理未完成的部分。这不需任何额外配置，也无需使用 `--force`。

### 运行监控

任务运行时，可实时查看进度：

- **任务列表**中显示当前进度百分比
- **运行日志**显示具体处理到哪个文件
- 右侧面板显示运行状态

### 完成标志

任务状态变为 `done`，文件统计面板显示解析结果摘要（符号数、边数、社区数等）。

### 重跑机制

> **AST 解析任务成功后不可直接重跑**，这是为了维护分析数据的一致性。因为后续的 AI 分析和文档生成都依赖 AST 解析结果，如果允许部分覆盖会导致数据不一致。

需要重新解析时，请按以下步骤操作：

1. **删除原有任务** — 在任务列表中找到已完成的任务，点击删除
2. **创建新任务** — 按照 [第 3 节](#3-创建分析任务) 的步骤创建同名任务并运行

如果只是修改了项目代码（增删文件），也可以使用 **同步** 功能更新文件索引后重新创建任务。

### 删除缓存

分析过程中产生的缓存数据（文件摘要、社区结果等）存储在本地数据库中。如果需要清理：

1. **单个项目缓存** — 在任务详情中选择 **清除缓存**，可选择清除指定表（如文件摘要、社区结果等）
2. **全部缓存** — 在设置中可清除所有项目的分析缓存

### 强制覆盖

某些 LLM 分析步骤支持 `--force` 参数，会忽略已有的缓存结果，强制重新生成：

```bash
# 在 AI Chat 中使用 /pipeline --force 重新运行完整流水线
/pipeline --force

# 强制重新生成架构概览
/overview --force

# 强制重新分析组件（忽略已有结果）
/analyze_components --force
```

### 失败处理

| 现象 | 原因 | 处理 |
|---|---|---|
| 任务一直停留在 `pending` | 后端繁忙或队列阻塞 | 重启应用后重试 |
| 任务运行中卡住 | 某个文件解析超时或内存不足 | 减少分析范围，排除大文件目录 |
| 解析结果符号数为 0 | 项目语言未被 Tree-sitter 支持 | 检查支持的语言列表（18+ 主流语言） |
| 边数很少或为 0 | 项目使用了非标准导入语法 | 不影响，后续 LLM 分析仍可进行 |

## 5. 架构分析与可视化

> 截图: `docs/images/usage/zh/community-graph.png`

分析任务完成后，在任务列表中点击任务进入分析视图：

### 5.1 社区结构图

- 图形中央展示项目的**社区结构图**（包含/调用关系）
- 每个节点代表一个"社区"（功能模块）
- 节点大小表示模块规模，颜色表示层级
- 支持交互操作：
  - **拖拽** — 移动节点
  - **滚轮** — 缩放
  - **点击** — 查看社区详情
  - **右键** — 上下文菜单（下钻、查看文档、存入便签）

### 5.2 切换视图

- **包含关系图 (INCLUDE)** — 显示模块间的包含/依赖关系
- **调用关系图 (CALL)** — 显示函数级的调用关系
- **热力图** — 按文件维度展示模块分布
- **文件形态** — 从组件视角切换到文件视角

### 5.3 层级下钻

点击社区节点或右键选择"下钻"，可以查看该模块内部子结构，逐层深入理解架构。

### 失败处理

| 现象 | 原因 | 处理 |
|---|---|---|
| 图渲染不出来 | 节点/边数过多 | 尝试缩小分析范围或降低粒度 |
| 社区数量异常 | 聚类参数不合适 | 调整社区发现参数（需代码修改） |
| 视图与代码不符 | 分析结果不够完整 | 重新运行任务，确保选择了正确的分析类型 |

## 6. AI 辅助分析

> 截图: `docs/images/usage/zh/architecture-overview.png`

### 6.1 生成架构概览

在报告视图中，点击 **生成架构概览**，系统将：

1. 收集社区分析结果和文件摘要
2. 调用 LLM 综合分析
3. 生成 Markdown 格式的架构文档

### 6.2 组件分析

在社区结构图中选择特定社区，可以：

- **查看组件详情** — 显示该组件的关键文件、符号和依赖
- **AI 分析组件** — 让 LLM 分析该组件的功能、架构角色和依赖关系
- **命名组件** — 为社区赋予有实际语义的名称（替代默认的社区编号）

### 6.3 LLM 分析耗时预估

> 以下为**单并发、单次调用**的参考值。LLM 推理速度因模型和硬件差异极大。

#### 预摘要（每 100 个文件）

| 模型类型 | 每 100 个文件 |
|---|---|
| 本地模型（Qwen3.6-9B 等, ~10-20 tok/s） | 30 - 60 分钟 |
| 云端模型（DeepSeek V4 Flash 等） | 5 - 15 分钟 |

#### 组件分析（每个社区）

每个社区的 LLM 分析包含：读取社区子图 → 批量摘要文件 → 综合分析 → 输出 JSON。单社区耗时：

| 模型类型 | 每个社区 |
|---|---|
| 本地模型（Qwen3.6-9B 等） | 3 - 8 分钟 |
| 云端模型（DeepSeek V4 Flash 等） | 30秒 - 2分钟 |

> **当前限制**：组件分析涉及多轮工具调用（读取文件、搜索符号、摘要文件），目前为**单请求串行处理**，不支持内部并发。过大的并发会加重本地模型负载且收益有限，不推荐对本地模型使用高并发。如有大量社区需要分析，建议本地模型过夜运行，或考虑使用云端模型加速。

举例：项目有 30 个社区，本地模型单请求串行分析完所有组件约需 **90 - 240 分钟**。

#### 架构概览（单次 LLM 调用）

| 模型类型 | 耗时 |
|---|---|
| 本地模型 | 3 - 10 分钟 |
| 云端模型 | 30秒 - 2分钟 |

#### 完整流水线总计

| 项目规模 | 社区数 | 本地模型（单并发） | 云端模型（单并发） |
|---|---|---|---|
| 小型 | 5 - 10 | 30 - 90 分钟 | 5 - 20 分钟 |
| 中型 | 10 - 30 | 2 - 6 小时 | 20 - 60 分钟 |
| 大型 | 30 - 100 | 6 - 20 小时 | 1 - 4 小时 |

> **并发说明**：组件分析目前为单请求串行处理，不支持内部并发。本地模型建议默认单并发运行，过夜处理大量社区。

### 替代方案：使用预分析项目

如果本地分析耗时过长，或本地模型能力不足以满足需求，可以：

1. 访问 **[topocode.cn](https://topocode.cn)** 注册账号
2. 在平台上搜索或浏览已经预分析好的开源项目
3. **关联本地代码**：将预分析结果与本地源码目录手动关联，即可在本地应用中查看架构文档和图表
4. **仅浏览文档**：也可以不关联代码，直接在平台上查看项目的架构分析文档

预分析项目由云端高性能模型完成分析，质量更高、等待时间为零。

### 6.4 组件分析重跑与模型切换

如果对某组件的分析结果不满意或发现错误，**无需重新运行整个任务**，可以**单选单步重跑**：

#### 操作流程

1. **在社区结构图中找到目标组件**（节点）
2. **右键点击该组件节点**，弹出上下文菜单
3. 选择 **AI 分析组件** 或 **重新分析**
4. 系统会**仅对该单个组件**重新发起 LLM 分析请求，不影响其他组件的结果

#### 更换模型重跑

重跑前可以切换到性能更高的模型：

1. 进入 **设置 → 模型配置**
2. 添加或切换到更强大的模型（如从 Qwen3.6-9B 切换到 DeepSeek V4 Flash）
3. 确保新模型已设置为**默认模型**
4. 返回分析视图，对目标组件执行**单选重跑**

新模型会立即生效，重跑结果将使用新模型生成。

#### 适用场景

| 场景 | 操作 |
|---|---|
| 某个组件命名不准确 | 单选该组件 → 重跑 → 或手动编辑名称 |
| 组件功能摘要过于简略 | 单选该组件 → 重跑（或在 Chat 中用 `/analyze_components --force`） |
| 部分组件结果正确，部分错误 | 仅对错误组件**单选重跑**，正确的不受影响 |
| 想用更强模型提升分析质量 | 设置新模型 → 单选组件 → 重跑 |
| 全部结果都不满意 | 使用 `/analyze_components --force` 强制全部重跑 |

### 6.5 截断执行与跳过已完成

#### 截断执行（部分分析）

如果项目过大，可以在分析时指定只处理部分社区：

- **在社区结构图中选择目标社区节点**
- 右键选择 **分析此组件** — 仅对该社区及直接关联的子社区执行 LLM 分析
- 或使用 `/analyze_components` 命令时在 Chat 中指定具体组件

#### 再次执行跳过已完成

LLM 分析支持**断点续跑**机制：

- **不使用 `--force` 时**：再次运行分析，系统会检查已有结果，**自动跳过已完成的部分**，仅分析未完成的组件
- **使用 `--force` 时**：忽略所有已有缓存，全部重新生成
- 这适用于：分析中途中断、新增少量文件后增量分析、仅想补充部分组件结果

```bash
# 仅补跑未完成的组件（跳过已完成的）
/pipeline

# 强制全部重跑（忽略所有缓存）
/pipeline --force
```

### 6.6 预摘要 (Pre-summary)

对于大型项目，可先运行预摘要：

1. 在任务详情中点击 **预摘要**
2. 系统按文件重要性排序，优先摘要核心文件
3. 摘要结果被缓存，后续 LLM 分析可直接使用

### 失败处理

| 现象 | 原因 | 处理 |
|---|---|---|
| LLM 调用超时 | 模型响应慢或网络问题 | 检查模型配置，尝试本地模型或降低 max_tokens |
| 分析结果为空 | 社区数据不足 | 确保任务分析完整，确认社区发现步骤已完成 |
| Token 耗尽 | 项目过大 | 缩小分析范围，或使用更大上下文的模型 |
| 组件命名不准确 | LLM 对上下文理解偏差 | 手动编辑命名，或提供更详细的项目摘要 |

## 7. 文档查看

> 截图: `docs/images/usage/zh/subdoc-viewer.png`

Web 文档服务提供完整的文档浏览体验，访问 `http://localhost:3456`：

### 7.1 首页文档列表

- `/` — 显示所有项目及其分析任务
- 已完成的任务显示绿色圆点，可点击查看文档
- 支持搜索和分页

### 7.2 文档查看器 (`/doc`)

- 左侧显示文档内容（Markdown 渲染）
- 右侧显示社区结构图
- 支持 Mermaid / PlantUML 图形渲染
- 工具栏：
  - **跟随模式** — 拖拽节点时关联节点跟随移动
  - **组件形态/文件形态** 切换
  - **关系图/热力图** 切换
  - **筛选器** — 搜索和过滤节点
  - **复原** — 重置布局

### 7.3 便签功能

- 在文档中选中文本后可**存入便签**
- 便签可以编辑、引用、发送给 AI 分析
- 支持按项目和排序筛选

### 失败处理

| 现象 | 原因 | 处理 |
|---|---|---|
| Web 页面打不开 | HTTP 端口未启动 | 检查设置中 HTTP 端口配置，确认端口未被占用 |
| 文档内容为空 | 未生成摘要文档 | 先运行 AI 概览生成或预摘要 |
| 图形显示异常 | Mermaid/PUML 语法问题 | 检查社区分析结果中的图形代码 |
| 页面显示"Backend not ready" | 后端尚未就绪 | 等待后端启动完成后刷新页面 |

## 8. AI Chat 对话

> 截图: `docs/images/usage/zh/ai-chat.png`

AI Chat 通过 Web 服务提供（`http://localhost:3456/chat`），无需 Electron，任何浏览器即可使用。

### 8.1 开始对话

1. 访问 `http://localhost:3456/chat`
2. 在左侧会话列表点击 **+ 新建会话**
3. 在底部输入框输入问题

### 8.2 对话能力

- **项目架构问答** — 询问项目结构、模块职责、代码组织方式
- **符号查询** — 搜索特定函数、类、接口的定义和调用关系
- **代码解释** — 解释代码逻辑和设计模式
- **架构建议** — 基于分析结果提出架构改进建议

### 8.3 工具调用

AI 助手可以调用工具来获取项目信息：

- `search_symbols` — 搜索符号定义
- `read_file` — 读取文件内容
- `summarize_file` — 批量摘要文件
- `get_community_subgraph` — 获取社区子图
- `get_call_chain` — 获取调用链

对话中 AI 会自主决定何时调用工具，无需手动干预。

### 8.4 Chat 命令与参数

AI Chat 支持以下斜杠命令，用于触发后端分析工作流：

| 命令 | 说明 | 支持参数 |
|---|---|---|
| `/overview` | 生成项目整体架构概览文档 | `--force` 忽略缓存重新生成 |
| `/analyze_components` | 对当前项目的社区进行逐组件 LLM 分析 | `--force` 强制覆盖已有结果；`-L zh/en` 输出语言 |
| `/presummary` | 运行文件预摘要，为核心文件生成摘要缓存 | `--force` 重新生成 |
| `/pipeline` | 运行完整分析流水线（预摘要 → 组件分析 → 概览） | `--force` 重新生成；`-L zh/en` 输出语言 |

参数示例：

```bash
# 完整流水线，英文输出，强制覆盖
/pipeline -L en --force

# 仅重新生成架构概览
/overview --force

# 重新分析所有组件
/analyze_components --force
```

> **注意**：组件分析涉及多轮工具调用，目前为**单请求串行处理**，`-j` 并发参数不适用。

### 8.5 便签集成

在文档查看器中选中的文本会自动存入便签，在 Chat 界面中可以：

- 查看和管理便签草稿
- 将便签内容发送给 AI 分析
- 引用文档中的内容作为对话上下文

### 失败处理

| 现象 | 原因 | 处理 |
|---|---|---|
| 对话无响应 | LLM 模型未配置或网络异常 | 检查模型配置，确认模型可用 |
| AI 回复与问题不相关 | 上下文不足或模型选择不当 | 补充项目背景信息，或切换更强的模型 |
| 工具调用失败 | 项目数据索引不完整 | 确保分析任务已完成，尝试重新运行 |
| 对话历史丢失 | 浏览器存储被清除 | 会话数据存储在 localStorage 中，避免清理 |

## 9. 基于知识库的分析对话

> 截图: `docs/images/usage/zh/knowledge-chat.png`

知识库功能用于持久化存储和管理架构分析文档。知识库是后续迭代的重点，目标是成为与用户认知高度契合的**外脑知识库**，不仅静态存储，未来还将支持通过多种对接方式，帮助用户指挥驾驭其他 Agent 工具，实现知识的**存储 → 分析 → 使用**闭环。

### 9.1 知识库入口

- 在左侧导航栏点击 **知识库** 图标
- 访问 `http://localhost:3456/chat` 中的便签功能

### 9.2 文档管理

- **查看** — 浏览已保存的架构分析文档
- **搜索** — 按关键词搜索文档内容
- **编辑** — 修改文档内容和标签

### 9.3 基于知识库的对话

在 AI Chat 中，可以引用知识库内容作为对话上下文：

1. 先在文档查看器中**选中文本 → 存入便签**
2. 切换到 Chat 界面，便签自动同步
3. 在输入框中引用便签内容（支持 #序号 引用）
4. AI 会基于引用材料进行分析回答

### 9.4 对话持久化与跨会话引用

- AI Chat 的对话内容已**自动持久化**存储在本地，刷新页面或关闭浏览器后不会丢失
- 持久化的对话本身即可作为上下文使用：在 **A 会话**中可以通过标明 **B 会话的会话 ID**，引用 B 会话的内容进行分析。例如在 Chat 输入框中提及 `@session:xxx` 即可关联指定会话的内容
- 当前未将对话纳入知识库，**并非缺少存档功能**，而是对话内容尚未规范化、结构化，直接入库会导致知识库质量不可控
- **未来版本**会对对话内容进行结构化提炼后合并到知识库，届时重要分析结论可一键入库

### 失败处理

| 现象 | 原因 | 处理 |
|---|---|---|
| 便签未同步 | 页面缓存问题 | 刷新 Chat 页面 |
| 引用未生效 | 便签格式错误 | 使用 `#序号` 格式引用（如 `#1`） |
| 存档失败 | 存储空间不足 | 清理旧存档或扩大存储配额 |

```bash
# 查看后端日志

cd backend-core
python main.py --http-port 3456
```

### 10.2 端口冲突

如果 5671/5680/3456 端口被占用：

1. 修改 **设置 → 通用设置** 中的 HTTP 端口
2. 或通过环境变量指定：
   ```bash
   export ZMQ_DEALER_PORT=5672
   export ZMQ_PUB_PORT=5681
   ```

### 10.3 内存不足

大型项目分析可能消耗较多内存：

- 建议分配至少 4GB 内存给应用
- 在启动参数中设置内存限制：`--memory-limit 4096`
- 减少分析任务并发数
