# 版本管理 & 导出 — 讨论记录

> 日期：2026-06-22
> 状态：讨论稿，待决策，不做开发

---

## 一、背景

AI Coding 效率极高（一小时数万行），TopoCode 需要解决的核心问题：

1. **理解 AI 写了什么** — 架构层面的变更是什么
2. **检验是否符合要求** — 代码是否遵循架构约定
3. **发现潜在问题** — 循环依赖、层间违规、Hub 过载
4. **辅助架构审阅** — 让人能做高效的架构级 Code Review

而这一切的前提是：**架构变更的版本管理**。

---

## 二、现有方案分析

当前 TopoCode 存在**两套并行的版本管理机制**：

### 2.1 SnapshotStore + DiffEngine（细粒度：文件/符号/依赖级）

**位置：** `backend-core/change_tracker/`

- 独立 SQLite 库 `snapshots.db`，keyed by `commit_hash`
- 存储文件 hash、符号列表、依赖列表
- Diff 3 维：文件级 → 符号级 → 依赖级（第 4 维"调用链"已定义未实现）
- 风险模型：5 级（NONE → CRITICAL），基于符号 kind/name/signature 启发式
- ImpactAnalyzer：识别影响文件、测试、高风险变更
- 版本上限：20 个/项目

### 2.2 arch_timeline（粗粒度：社区/架构级）

**位置：** `backend-core/task_manager.py`（project DB 内）

- 两张表：`arch_timeline` + `arch_timeline_communities`
- 存储 L0 社区全量快照（节点列表、边列表、LLM 命名/摘要/图表）
- Diff 方式：社区 ID 集合差集
  ```python
  added   = curr_ids - prev_ids
  removed = prev_ids - curr_ids
  risk    = "high" if removed > 0 else ("medium" if added > 5 else "low")
  ```
- 前端完整集成（TimelineDialog，有保存/对比/导出/晋升/删除）
- 是当前实际可用的架构版本管理方案

### 2.3 现有导出功能（已设计未启用/不完整）

| 功能 | 位置 | 状态 |
|------|------|------|
| `graph.exportSnapshots` → `.topocode/archive/*.jsonl` | `task_manager.py:3802` | 已启用，但只是 dump，无版本语义 |
| `system.exportProject` → `.topocode-archive` zip | `core_service.py:681` | 后端完整，前端无入口，未启用 |
| `system.importProject` ← `.topocode-archive` zip | `core_service.py:730` | 同上 |
| `CLI arch export --format --output` | `main_cli.py:245` | handler 为 stub，打印"功能开发中" |
| 前端"导出架构"按钮 | `CommunityGraphView.vue:952` | placeholder，弹出空白页 |
| KnowledgePage 导入/导出按钮 | `KnowledgePage.vue:183` | 有按钮无 handler |

### 2.4 现有方案的根本问题

1. **数据锁在 SQLite 里** — 外部不可见、不可 `git diff`、不可 PR 审阅
2. **两套系统互不打通** — SnapshotStore 的文件数据和 arch_timeline 的社区数据无关联
3. **arch_timeline diff 过于粗糙** — 仅 ID 集合差集，不比较节点内容
4. **自建版本管理是重复造轮子** — Git 已是最成熟的版本管理系统
5. **所有版本管理 CLI 命令均为 stub** — `track` / `diff` / `arch` 均未实际实现
6. **ArchSentinelWorkflow 有导入 bug** — `tool_factory.py` import 了不存在的 `_SnapshotTool` / `_SaveDeltaTool`

## 三、方案选择

### 选项 A：SQLite 自管版本（当前路线）

架构分析数据存在 TopoCode 自己的 SQLite 中，自建 DiffEngine 做版本对比。

**问题：**
- 架构分析数据是**大体积结构化数据**（图结构、LLM 长文本），在 SQLite 中管理版本变更笨重
- DiffEngine 需自己维护（且第 4 维调用链 Diff 一直没做）
- 数据无法在 TopoCode 之外访问
- 无法利用 Git 的 diff/log/branch/merge/PR 生态

### 选项 B：静态导出 + Git 管理（推荐）

架构分析数据**导出为文本文件**，由 **Git 独立仓库**（与源码仓库分开）管理版本。

**本质变化：**
- TopoCode 不再做版本管理（删除 SnapshotStore、arch_timeline、DiffEngine 等）
- TopoCode 只做一件事：**把当前架构状态导出为静态文本文件**
- 版本管理的所有工作交给 Git

## 四、推荐方案：纯静态导出

### 4.1 核心理念

```
                   TopoCode 职责边界
┌──────────────────────────────────────────────────────────┐
│  Codegraph 分析                                          │
│  (AST 解析 → 社区检测 → LLM 命名/摘要)                     │
│                        │                                 │
│                        ▼                                 │
│  静态导出器 (ArchExporter)                                 │
│  当前状态 → 确定性排序 → 多文件文本写入                      │
└────────────────────────┬─────────────────────────────────┘
                         │
                         ▼
                ┌─────────────────┐
                │ 文本文件目录      │← 用户自行决定如何 Git 管理
                │ ├ communities   │   - 独立仓库
                │ ├ symbols       │   - 源码仓库子目录
                │ └ report/       │   - 仅团队共享目录
                └─────────────────┘
```

TopoCode **不关心文件怎么存、怎么 diff、怎么回滚**。这些全是 Git 的事。

### 4.2 导出文件格式

```
输出目录/
├── topo-arch.json               # 版本元信息 + 源 commit
│   { "topo_version": "1.0",
│     "exported_at": "2026-06-22T10:30:00Z",
│     "source_commit": "abc123def",
│     "source_branch": "feature/xxx",
│     "project_name": "...",
│     "community_count": 7,
│     "file_count": 124,
│     "symbol_count": 47981 }
│
├── communities.json              # L0 社区结构（diff 核心对象）
│   [{ "id": "L0-0001",
│      "name": "路由处理模块",       ← LLM 命名或手动命名
│      "level": "L0",
│      "edge_type": "INCLUDE",
│      "node_count": 12,
│      "nodes": [
│        {"file": "src/router/index.ts", "symbols": ["Router"]}
│      ],                         ← 按 file 路径排序
│      "depends_on": ["L0-0003"]  ← 按 id 排序
│    }, ... ]                     ← 按 id 排序
│
├── dependency-matrix.json        # 社区间依赖 N×N 矩阵
│   { "edge_type": "INCLUDE"
│     "communities": ["L0-0001", "L0-0002", ...],
│     "matrix": [[0,1,0],[0,0,1],[1,0,0]] }
│
├── symbols-index.json            # 符号索引（大文件，可选 git LFS）
│   [{ "file": "src/foo.ts",
│      "symbols": [
│        {"name": "doSomething", "kind": "function", "line": 42}
│      ]}, ... ]
│
└── report/                       # LLM 生成文档（可选，需 LLM 调用）
    ├── arch-overview.md
    └── diagrams/
        ├── dep-graph.mermaid
        └── call-graph.mermaid
```

**关键设计原则：**
- 每个文件是合法的 JSON（非 JSONL），可用 `jq` 等标准工具处理
- 所有数组按稳定 key 排序（`id`、`file_path`），保证确定性输出，`git diff` 有意义的行对比
- 不包含任何 SQLite 内部 ID 或数据库实现细节
- 文件自描述——脱离 TopoCode 也能理解

### 4.3 CLI 接口

```bash
# 导出当前架构状态到指定目录（核心功能）
topocode export --out ~/arch-repo/v20260622

# 导出 + 自动 git commit（--git-commit 只是方便的封装）
topocode export --out ~/arch-repo/v20260622 --git-commit -m "arch: after auth refactor"

# 导出时附带 LLM 架构报告
topocode export --out ./arch-report --with-report
```

`export` 是唯一与"版本"相关的命令，原有 `track` / `diff` / `arch` 全部移除。

### 4.4 前端改造

```
移除：TimelineDialog.vue 及全套版本管理 UI，约 387 行
新增：ExportDialog.vue（极简），约 120 行

  <export-dialog>
    ├─ 输出目录选择（文本框 + 浏览按钮）
    ├─ 选项：导出后自动 git commit（含 commit message）
    ├─ 选项：生成架构报告（LLM）
    └─ [导出] 按钮
```

### 4.5 用户端工作流示例

```bash
# ── 初始化（只需一次）──
mkdir -p ~/arch-repo && cd ~/arch-repo && git init

# ── AI 编码后，开发者导出架构快照 ──
cd ~/project
topocode export --out ~/arch-repo/v20260622 --git-commit -m "after auth refactor"

# 输出:
#   ✅ 已导出 7 个社区、124 个文件、47981 个符号
#   ✅ 已 git commit ~/arch-repo (v20260622)

# ── 审阅者查看架构变更 ──
cd ~/arch-repo
git log --oneline           # 架构变更历史
git diff HEAD~1 -- communities.json   # 社区结构变化
git diff HEAD~1 -- dependency-matrix.json  # 依赖关系变化

# ── PR 中自动检测架构变化 ──
# .github/workflows/arch-check.yml
git diff HEAD~1 HEAD --name-only --exit-code communities.json \
  && echo "架构未变化" \
  || echo "架构有变更，需人工审阅"
```

## 七、待决策点

1. **导出触发方式** — 仅 CLI 即可，还是 GUI 也需要"导出"入口？
   - 仅 CLI：代码改动最少，适合自动化工作流
   - GUI + CLI：普适性更强
2. **报告（report.md）的生成** — 导出时自动触发 LLM 生成，还是单独靠 Skill 生成？
   - 自动：一步到位，但耗时数秒
   - 单独：灵活但多一步操作
3. **现有 arch_timeline 旧数据** — 是否写迁移脚本导出为文本，还是直接清理？
   - 迁移：用户历史数据不丢失
   - 清理：代码更干净
