## 第一部分 · 微调方向为什么成立

### 1.1 产品侧的四个先决条件（已具备）

1. **任务高度模式化**：`prompt_templates.json` 全部 16 个模板（community_name / edge_explain / src_to_pseudocode / 预摘要 / 组件分析 / 架构生成…），输入输出模式固定、调用海量重复——小模型微调收益最大的场景形态
2. **分发链路现成**：provider 体系全部 OpenAI 兼容（Ollama / LM Studio 一等公民），微调产物导出 GGUF 后对产品只是"一个新模型条目"，零架构改动
3. **AST 锚点是安全网**：LLM 只准引用符号名 → 服务端解析为真实 `AstNodeRef`，小模型幻觉损害被结构性限制——通用工具不敢用 0.8B~4B 的胆量来自这里
4. **与 L/M/H 分级天然衔接**：微调是"L 级零 LLM"与"9B 本地大模型"之间的新档位（S 档），成本梯度由三级变四级

### 1.2 核心主张：不做"全能小模型"，做"任务路由"

按 **频率 × 难度** 分层，微调只吃高频中低难度层（匹配矩阵见路线图 §6.2）：

| 管线任务 | 频率 | 微调档位 | 硬件下限 |
|---|---|---|---|
| 社区/组件命名 | 极高 | 0.8B~1B（Qwen3.5-0.8B / MiniCPM5-1B） | 纯 CPU |
| 边缘/源码解释、伪代码 | 高 | 1~2B | CPU/入门卡 |
| 文件预摘要（数小时级瓶颈所在） | **最高** | 2B（Qwen3.5-2B / MiniCPM5-2B） | 4~6G 显存 |
| 语义资产 M 级归纳、变更摘要 | 高 | 2~4B | 6~8G 显存 |
| 组件分析（agentic，带工具调用） | 中 | 4B（Qwen3.5-4B） | 8G 显存 |
| 整体架构生成 / 需求 agent / chat 对话 | 低 | 不微调（M/H 档） | — |

**选型倾向**：Qwen3.5 系为主力（0.8B→4B 梯度完整、代码与函数调用底子强、商用许可友好）；MiniCPM5 为边缘端备选（端侧推理效率）。**对标关系**：现状 README 推荐 Qwen3.6-9B-Q4 做架构解析，微调目标是 **4B 微调版在管线任务上追平 9B 通用版**——无独显/小显存用户跑全 LLM 管线成为可能。

### 1.3 数据战略：管线自造血（最值钱的部分）

```
热门开源项目（资源中心语料）
   │  教师模型（云端旗舰）跑完整管线
   ├── (管线真实 prompt, 教师 completion) 对 …… 蒸馏训练集
   ├── L 级 codegraph 确定性事实 ……………………… 过滤脏样本（符号不存在/行号臆造直接丢弃）
   └── 用户采纳行为（命名/摘要是否被接受）……… 后期 DPO 偏好数据
```

- **采集近零成本**：`openai_compat.py` 已记 `[LLM_REQ]` 全量日志，补本地脱敏采集器落 jsonl 即可（默认不出本机，守隐私承诺）
- **编码侧语料复用**：开源项目真实 commit 对（测试通过前/后）+ mandate 约束注入
- **资源中心协同**：预分析项目 = 获客内容 + 训练语料；微调模型 = 资源中心分发物 → 商业化路径 a/b 同时加强
- **终局**："TopoCode 认证的分析模型"成为可分发资产，训练数据闭环是通用竞品难以复制的护城河

### 1.4 工程与评测要点（摘要）

- **方法**：QLoRA 按任务组训 adapter（4B 单卡 24G 可训）；训练目标必须含**结构化 JSON 输出 + function-call 格式**（对齐 `get_tool_definitions` 四 toolkit 与 output_schema）——这是小模型上管线的生死线
- **成对版本**：prompt 模板与微调模型成对版本化，模板改动触发回归评测，防线上静默漂移
- **分发**：Q4_K_M/Q5 GGUF + Ollama Modelfile
- **评测门禁（管线级，不用通用 benchmark）**：结构化输出合法率 ≥99% / 符号可解析率（AST 锚点命中）≥97% / 预摘要相对教师质量 ≥85% / 组件命名采纳率对标 9B 通用版 ±5% / 端到端微调 4B ≈ 通用 9B 且耗时 ↓50%

任务排期（L1~L7）与验收标准见路线图 §6.6。

## 第二部分 · 闭环三环节的小模型胜任力论证

> 问题：① 需求围栏/方案安全围栏生成，小模型能否胜任？② 高质量围栏之上的编码，小模型能否胜任？③ 编码测试中的 bug 修复需要什么级别模型？
> 结论总表见路线图 §6.3，本文为论证全文。

### 2.1 Q1 围栏生成：把"裁决"与"编译"拆开

**结论：裁决不能下沉（H 档保留），编译与验证可下沉（微调 4B / 2~4B）。**

围栏生成本质是三类不同性质的子任务：

| 子任务 | 本质 | 小模型胜任性 | 依据 |
|---|---|---|---|
| **裁决**：判断需求用低/中/高配架构、发现需求冲突、权衡非功能指标 | 开放性推理，答案不在输入里 | ❌ 需 32B+/云端旗舰 | 围栏错误是**传播成本最高的错误**，把整个下游带偏；此处的省钱是假省钱 |
| **编译**：已裁决模式实例化为具体约束（"中配 → 三层包结构 + 禁止跨层注入"式禁则展开）、验收标准结构化、Context_Matrix / Arch_Spec 格式化 | 模式 → 实例映射，高度模式化 | ✅ 微调 4B | plan-A 的三轴模板（X 本体 × Y 抽象 × Z 治理 × 低/中/高配）本质是巨大查找表——**微调最擅长的就是背表并正确查表** |
| **验证**：围栏自洽性检查、约束锚定真实符号、需求覆盖度查漏 | 分类/校验任务 | ✅ 微调 2~4B | 生成-验证分离中的验证侧；错误代价低（可重生成） |

**两个结构性加持**：

1. `req_agent` 的 harness 已是 clarify/collect → 结构化产出，输出 schema 固定，微调对齐成本低
2. **语义资产给围栏供事实**——"依据 → 约束"的映射是小模型可学的；小模型怕的是"依据不足时的自由发挥"，而 TopoCode 的围栏锚定在 codegraph 事实上。**围栏质量的上限来自资产库而不是模型**，这是与"裸 prompt 生成架构图"工具的本质区别

### 2.2 Q2 围栏之上编码：可以胜任，但有四个前提

**原理**：约束越强，代码生成越从"自由生成"退化为"约束求解"，对模型能力的要求单调下降（plan-B 的"从自由生成变为约束求解"正是此意）。

四个前提（产品架构已设计其中三个）：

| 前提 | 现状对应 |
|---|---|
| ① 任务原子化：Task_Graph 拆到原子任务 + 依赖标注，单函数/单文件粒度 | plan-B Phase 3 已设计 |
| ② 约束密度：mandate 细到函数签名、禁则、验收标准级 | 路线图 P2-T4（mandate 质量加固） |
| ③ 上下文精确注入：语义资产/AST 锚点压缩上下文，绕开小模型长上下文短板 | semantic_assets 已有 |
| ④ 验收自动化：单测门禁即时反馈，坏输出进不了主干 | arch_unit_tests 已有 |

**胜任区间**（S 档 4B，简单层 2B）：单函数实现、CRUD/样板层、测试用例生成、机械迁移、格式适配。
**不胜任区间**（回退 M 档 9B+）：跨文件重构、依赖隐式全局约定的代码、性能敏感算法、设计性代码。
**训练数据**：开源项目真实 commit 对（测试通过前/后）+ mandate 约束注入，与资源中心语料复用。

### 2.3 Q3 bug 修复：级别分四级，且由反馈回路质量决定

**核心洞察：修复所需模型级别 ∝ 反馈回路质量的倒数。** 失败可复现、错误信息结构化、测试最小化做得越好，所需模型越小。

| 级别 | 典型形态 | 所需模型 | 原因 |
|---|---|---|---|
| **L1** | 编译错/类型错/lint/import 缺失 | 规则优先，兜底 0.8~2B | 错误信号完全结构化（编译器已定位） |
| **L2** | 测试失败、栈信息明确、症状≈根因 | **2~4B 微调可胜任** | "失败输出 + 局部代码 → patch"是模式化映射；训练对易构造（CI 历史 + 定位后 diff） |
| **L3** | 逻辑错误、症状≠根因、需跨文件推理定位 | **7~14B 本地 + 工具调用** | 需要假设-验证链（读代码/跑测试/查符号的 agentic 循环），小模型推理深度不够 |
| **L4** | 架构性缺陷、并发/时序问题、需求理解错误 | 云端旗舰 + 人工 | 需要全局模型与领域判断 |

两个附加结论：

1. **单测验收门禁会把大量 L3 降级为 L2**——所以修复模型的级别不是固定的，是自身工程能力决定的；这是"用工程换模型"的直接变现点
2. **修复循环的编排**（重试几轮、何时升级模型、何时上报人工）是 harness 规则问题，不消耗大模型智能

### 2.4 汇总：黄金路径的模型成本曲线是"哑铃型"

```
裁决 / mandate 生成      围栏编译 → 原子编码 → L1/L2 修复        L3 定位 / L4 攻坚
   (H 云端旗舰)          (S 微调 2~4B，调用量最大)              (M 9B ~ 云端)
       ▲                            ▲                                ▲
    少而贵                    多而廉 —— 微调主战场                  少而贵
```

**产品含义**：两头租云、中间自研。腰部（围栏展开/原子编码/L1-L2 修复）恰是调用量最大、模式最固定、微调 ROI 最高的区段，即路线图 L7 扩展轮的目标；而腰部的宽度由四个工程前提决定——**小模型的天花板是产品架构给的，不是模型本身给的**。
