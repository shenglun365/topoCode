# 架构感知功能讨论

> 日期：2026-06-22
> 背景：AI Coding 效率极高（一小时数万行），需要 TopoCode 协助用户理解 AI 写了什么、是否按需求编写、是否存在潜在问题，以及进行架构/组件级别的评审。

---

## 一、问题域

AI 编码速度快 → 人工审阅速度成为瓶颈，核心痛点：

1. **理解困难** — AI 写了数万行，人不知道改了哪里、改了什么
2. **合规无保障** — 没有人能逐行确认 AI 代码是否遵循架构约定
3. **风险不可见** — 潜在问题（循环依赖、层间违规、Hub 过载）藏在大批量代码中
4. **审阅效率低** — 传统逐行 Code Review 无法匹配 AI 产出速度

TopoCode 应该解决的是：**让架构变更「可知、可控、可审」**。

## 二、现有能力评估

### 2.1 已完成（可直接使用）

| 能力 | 状态 | 说明 |
|------|------|------|
| Codegraph 6 步索引流水线 | ✅ | AST 解析 → 引用解析 → 导入提取 → 框架合成 → Louvain 社区检测 → 摘要生成 |
| DiffEngine — 三维对比 | ✅ 缺 1 维 | 文件级(hash)、符号级(增删改+风险)、依赖级；调用链级未实现 |
| SnapshotStore — 快照存储 | ✅ | SQLite 存储，每个项目最多 20 版本，线程安全 |
| ArchSentinelWorkflow — 架构哨兵 | ✅ 含 bug | 社区级 diff（新增/删除/变更社区）+ LLM 语义摘要 |
| ImpactAnalyzer — 影响分析 | ✅ | 识别影响文件、受影响测试、高风险变更 |
| ComponentAnalystWorkflow | ✅ | LLM 批量分析组件命名/职责/关键文件/依赖 |
| AgenticComponentAnalystWorkflow | ✅ | ReAct 循环 + 工具调用的深度组件分析 |
| 四层认知模型 (AnalysisContext) | ✅ | 项目 → 社区 → 文件 → 符号，每层含 what/how/why |
| 6 个 MCP 架构认知工具 | ✅ | community / community_detail / arch_overview / diff / session_summary / quality_inspect |
| 13 个内置 Skill | ✅ | 可组合的多步编排能力 |
| 风险等级模型 | ✅ | NONE / LOW / MEDIUM / HIGH / CRITICAL |
| 可视化引擎 | ✅ | D3 / Mermaid / PlantUML / Cytoscape / Pixi 多引擎 |

### 2.2 存在缺陷或缺失

| 短板 | 影响 | 说明 |
|------|------|------|
| **调用链级 Diff** | ⛔ Diff 漏了最重要的维度 | DiffEngine 文档说 4 维，但只实现了 3 维（缺调用链） |
| **循环依赖检测** | ⛔ 严重的架构问题盲区 | `quality_inspect` 的 `focus: "cyclic_deps"` 枚举存在但无检测逻辑 |
| **架构规则引擎** | ⛔ 无法验证「是否按需求写」 | 没有 archguard 式规则（如「controller 不能直接依赖 DAO」） |
| **`skill_validate_arch_impact`** | ⛔ 空占位符 | "预测新模块影响" 完全未实现 |
| **`_SnapshotTool` / `_SaveDeltaTool`** | ⛔ 运行时可能崩溃 | `tool_factory.py` import 了不存在的类 |
| **耦合内聚度量** | ⛔ 无法量化架构健康度 | 无 Martin 指标（传入耦合/传出耦合/不稳定性/抽象性） |
| **趋势分析** | ⛔ 只有点对点对比 | 无法查看 N 个版本的架构演化趋势 |
| **CLI 集成** | ⛔ 命令行全为 stub | `track` / `diff` / `arch` 三个命令均打印"功能开发中" |
| **前端审阅工作流** | ⛔ 无专属审查界面 | 没有「代码审查 → 架构分析」的端到端交互 |
| **预期 vs 实际架构对比** | ⛔ 无合规报告 | 没有"预设架构 → 实际架构"差异分析 |

## 三、应对方案：三层架构审阅体系

### 第一层：变更感知基线（Weeks 1-2）

**目标：让用户 5 分钟看懂 AI 改了什么**

交付物：

1. **修复 `_SnapshotTool` / `_SaveDeltaTool` 导入 bug** — 使 ArchSentinel 可正常调用
2. **实现调用链级 Diff** — 新增/删除/修改的调用关系是架构变更最敏感的维度
   - 基于 SymbolGraph 的边对比（caller/callee 对）
   - 标注调用链中新增/移除的中间节点
3. **实现循环依赖检测**
   - 在社区图上运行 Tarjan/Johnson 强连通分量算法
   - 可视化标注环状依赖路径
4. **连通 CLI `track` 命令** — 对接 ArchSentinelWorkflow
   - `topocode track start` — 记录基线快照
   - `topocode track stop` — 对比 + LLM 变更语义摘要
5. **变更语义摘要增强** — 为变更生成可读性解释
   - 结合 git log + diff 数据 + 社区上下文
   - LLM 生成：「新增了轮询调度模块，它与现有模块 X/Y/Z 产生了新依赖...」

**输入/输出示例：**

```
$ topocode track start --tag "before-ai-edit"
→ 基线已记录 (commit: abc123)

# AI 编码之后...
$ topocode track stop
→ ═══ 架构变更报告 ═══
  新增文件: 12 | 修改文件: 8 | 删除文件: 3
  新增符号: 47 | 修改符号: 23 | 删除符号: 5
  新增调用链: 15 | 删除调用链: 3
  新增循环依赖: 1 ⚠️ [auth → db → cache → auth]
  风险等级: MEDIUM (score: 8)
  
  LLM 摘要:
  "AI 新增了「权限缓存模块」，在 auth 和 db 之间插入了缓存层。
   这消除了 auth→db 的直接调用（风险降低），但引入了新的
   auth→cache→db 的循环依赖（需确认是否是预期设计）。
   新增的 API 路由模块与现有中间件链兼容，无破坏性变更。"
```

### 第二层：架构规则引擎（Weeks 3-4）

**目标：自动判断 AI 代码是否「按规矩写」**

交付物：

1. **轻量声明式规则 DSL**

```yaml
# .topocode/arch-rules.yaml
rules:
  - name: "Controller 不能直接依赖 Repository"
    from: "**/controller/**"
    to: "**/repository/**"
    action: deny  # deny | warn
    severity: high

  - name: "Service 层必须通过接口依赖 Repository"
    description: "禁止直接 import 具体 Repository 实现类"
    from: "**/service/**"
    to: "**/repository/impl/**"
    action: deny
    severity: medium

  - name: "工具类不应依赖业务模块"
    from: "**/utils/**"
    to: "**/service/**"
    exclude: "**/utils/test/**"
    action: deny
    severity: critical

  - name: "UI 层只能依赖 Service 接口层"
    from: "**/ui/**"
    allow:
      - "**/service/*.ts"
      - "**/types/**"
    action: deny  # 超出 allow 列表的依赖均拒绝
    severity: high
```

2. **基于社区映射的规则**

可利用 Louvain 社区划分结果写规则。社区已有 AI 命名的名称，规则可直接引用社区名：

```yaml
  - name: "路由层不能调用数据层"
    from_community: "路由处理模块"   # 使用社区 AI 名称
    to_community: "数据访问层"
    action: deny
```

3. **预期架构录入 UI**

   在 TopoCode 前端增加"预期架构"配置界面：
   - 基于当前社区划分为蓝图，允许拖拽调整
   - 保存为 `预期架构快照`
   - 后续每次 `track stop` 自动对比预期 vs 实际

**效果：**

```
$ topocode track stop
→ ═══ 架构规则违反 ═══
  ❌ 违规: Controller 不能直接依赖 Repository
     controller/UserController.ts:42 → repository/UserRepo.ts
     severity: high
  
  ⚠️ 警告: 工具类不应依赖业务模块
     utils/formatHelper.ts:7 → service/OrderService.ts
     severity: critical

  总计: 2 项违规 (1 high, 1 critical)
```

### 第三层：AI 辅助人工审阅工作流（Weeks 5-6）

**目标：让人高效地做最终判断，而不是逐行读代码**

交付物：

1. **架构审阅 Dashboard（前端新页面）**

   聚合展示：
   - **变更概览** — 文件/符号/调用链增减统计 + 风险等级 + 趋势箭头
   - **按社区归类的变更列表** — 不是按文件名排序，而是按逻辑模块分组
   - **规则违反清单** — 红(deny)/黄(warn) 分色标注，可点击跳转到具体代码行
   - **社区级变更热力图** — 每个社区色块表示变更量、风险级别

2. **逐组件审阅模式**

   每次聚焦一个社区内的变更，组件内展示：
   - 该社区的 Mermaid 架构图（高亮本次修改的部分）
   - 修改符号的 before/after 签名对比（inline diff）
   - 影响范围图：「修改了 A → 影响社区 B/C/D」
   - LLM 对每个变更的解释：「这个修改的意图是什么」

3. **审阅记录追踪**

   - 标记状态：待审 / 已批准 / 需修改 / 已驳回
   - 支持在每个变更上添加审阅注释
   - 生成审阅报告（Markdown/PDF）
   - 审计日志（谁、什么时候、批准了什么）

4. **一键回滚建议**

   - 对高风险变更，自动计算回滚的影响面
   - 提供 `git revert` 命令预览
   - 标注回滚后哪些功能会受影响

## 五、待确认方向

1. **规则引擎粒度** — 轻量声明式 YAML DSL vs 扩展 LLM Agent 自主判断架构违规？
   - 前者的好处：确定性强、可测试、执行速度快
   - 后者的好处：灵活、可处理模糊规则、能给出解释

2. **审阅工作流定位** — 集成在 TopoCode Electron 桌面端 vs 独立 CLI 命令输出报告？
   - 桌面端：交互丰富、可视化强
   - CLI：适合 CI/CD、适合偏好终端的工作流
   - 合理方案：两者都有，CLI 输出结构化数据（JSON/Markdown），桌面端渲染

3. **AI 编码 Agent 对接优先级** — 优先对接 codex/claude code 等通用 Agent，还是优先做 MCP Server 增强？
   - MCP 是协议层：做好后任意 MCP-compatible Agent 都能用
   - Codex/Claude code 是应用层：可以看到实际效果，但绑定具体平台

4. **P0 优先级确认** — 循环依赖检测 + 调用链 Diff 是否为当前最高优先级？
   - 这两个是架构审阅"说服力"最关键但缺失的环节
   - 修复导入 bug 是前提条件（否则现有功能有运行时风险）
