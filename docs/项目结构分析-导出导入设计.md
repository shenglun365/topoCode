# 项目结构分析 — 导出导入设计

## 1. 背景

TopoCode 对项目的分析结果（符号节点、关系边、社区层级、LLM 分析摘要等）分布在多个 SQLite 数据库中。用户需要能将完整分析结果打包分享给其他用户，接收方在本地的 TopoCode 应用中导入后，可查看社区图、结构图、报告、AI 分析等全部内容，无需重新分析。

### 1.1 约束

- **不包含源码内容**——只含文件路径/语言/大小等元信息
- **接收方如需代码关联**（符号跳转/行级定位），需手动将对应版本的源码复制到导入目录
- **单文件分发**——以 `.topoexport` 格式传输

---

## 2. 数据范围

### 2.1 分析结果分布在 3 个数据库

| 数据库 | 路径 | 表 | 用途 |
|--------|------|----|------|
| 主库 | `~/.topocode/topoone.db` | `projects`, `analysis_tasks`, `analysis_task_runs`, `analysis_reports` | 项目信息、任务配置、运行记录、分析报告 |
| 项目库 | `{project_root}/.topocode/data/project.db` | `source_files`, `graph_node`, `graph_edge`, `graph_doc`, `community_hierarchy`, `community_llm_results`, `report_subdocs`, `file_summaries`, `arch_snapshots`, `arch_snapshot_communities`, `agent_task_history` | 分析核心数据 |
| 会话库 | `~/.topocode/sessions.db` | `llm_sessions`, `llm_messages` | 不包含在导出中（属于用户个人交互记录） |

### 2.2 导出范围

一个 `.topoexport` 包含**一个项目**的全部分析数据。任务级过滤通过在 `export-meta.json` 标记 `task_ids` 子集实现，数据文件不变，导入端按标记过滤写入。

## 3. 文件格式：`.topoexport`（gzip 压缩包）

### 3.1 内部结构

```
my-project.topoexport（gzip 压缩包，单文件）
  │
  ├── export-meta.json          ← 版本、时间、来源、统计
  ├── export-schema.sql         ← DDL（CREATE TABLE IF NOT EXISTS ...）
  ├── graph_node.jsonl          ← 每行一个完整 JSON 对象
  ├── graph_edge.jsonl
  ├── graph_doc.jsonl
  ├── community_hierarchy.jsonl
  ├── community_llm_results.jsonl
  ├── report_subdocs.jsonl
  ├── file_summaries.jsonl
  ├── source_files.jsonl
  ├── arch_snapshots.jsonl
  ├── arch_snapshot_communities.jsonl
  ├── analysis_tasks.jsonl
  ├── analysis_task_runs.jsonl
  └── analysis_reports.jsonl
```

### 3.2 格式规则

- 每个 `.jsonl` 文件无 BOM，无尾逗号，逐行 `\n` 分隔
- 每行是一个完整的 JSON 对象，字段名与目标表列名一致
- `export-schema.sql` 复用 `sqlite_ctx.py` 中对应表的 `CREATE TABLE IF NOT EXISTS` DDL
- `export-meta.json` 先读取，无需解压完整数据即可判断兼容性

### 3.3 `export-meta.json` 格式

```json
{
  "version": 1,
  "exported_at": "2026-06-28T12:00:00Z",
  "source_version": "0.1.0",
  "source_machine_id": "sha256[:16]",
  "description": "TopoOne-ui v2.3 架构分析结果",
  "project_name": "topoOne-ui",
  "project_language": "TypeScript",
  "task_ids": ["t1", "t2"],
  "stats": {
    "source_files": 168,
    "graph_nodes": 4823,
    "graph_edges": 12450,
    "graph_docs": 128,
    "community_llm_results": 128,
    "report_subdocs": 56,
    "arch_snapshots": 3,
    "analysis_tasks": 2,
    "uncompressed_bytes": 28600000
  },
  "anonymize_level": "none",
  "schema_hash": "sha256[:16]"
}
```

### 3.4 `export-schema.sql` 内容

从 `sqlite_ctx.py` 的 `PROJECT_DB_TABLES_SQL` 和 `MAIN_DB_TABLES_SQL` 中摘取导出涉及的表 DDL，包含索引但排除 `FOREIGN KEY`（导入端新建项目无关联约束）。例如：

```sql
CREATE TABLE IF NOT EXISTS graph_node (
    id TEXT PRIMARY KEY,
    task_id TEXT NOT NULL,
    kind TEXT NOT NULL,
    name TEXT NOT NULL,
    qualified_name TEXT NOT NULL DEFAULT '',
    file_path TEXT NOT NULL DEFAULT '',
    file_id TEXT DEFAULT '',
    language TEXT DEFAULT '',
    start_line INTEGER NOT NULL DEFAULT 0,
    start_col INTEGER NOT NULL DEFAULT 0,
    end_line INTEGER NOT NULL DEFAULT 0,
    end_col INTEGER NOT NULL DEFAULT 0,
    signature TEXT DEFAULT '',
    visibility TEXT DEFAULT '',
    is_exported INTEGER DEFAULT 0,
    is_async INTEGER DEFAULT 0,
    is_static INTEGER DEFAULT 0,
    docstring TEXT DEFAULT '',
    decorators TEXT DEFAULT '',
    type_parameters TEXT DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_graph_node_task ON graph_node(task_id);
CREATE INDEX IF NOT EXISTS idx_graph_node_kind ON graph_node(task_id, kind);
```

### 3.5 `.jsonl` 行示例

```
{"_table":"graph_node","id":"n1","task_id":"t1","kind":"class","name":"AppComponent","qualified_name":"AppComponent","file_path":"src/App.vue","start_line":1,"start_col":0,"end_line":100,"end_col":0}
{"_table":"graph_node","id":"n2","task_id":"t1","kind":"method","name":"onMounted","qualified_name":"AppComponent.onMounted","file_path":"src/App.vue","start_line":20,"start_col":4,"end_line":45,"end_col":5}
{"_table":"graph_edge","id":"e1","task_id":"t1","source_id":"n2","target_id":"n3","kind":"calls","provenance":"parser","line":22,"file_path":"src/App.vue"}
```

- 每行包含 `_table` 字段，流式写入时用于路由到对应表
- 写入时从行中移除 `_table` 再绑定参数

## 4. 导出流程

### 4.1 后端核心类

**文件**: `backend-core/export_manager.py`（新增）

```python
class ExportManager:
    """分析结果导出/导入管理器"""

    MAX_EXPORT_VERSION = 1

    def export_project(
        self, project_id: str,
        task_ids: list[str] = None,      # None = 全部任务
        anonymize_level: str = 'none',   # 'none' | 'mild' | 'full'
        output_path: str = None,
        description: str = '',
    ) -> str:
        """导出项目分析结果为 .topoexport 文件"""
        pass
```

### 4.2 导出步骤

```
用户选择「导出分析结果」
  │
  ├─ 1. 弹出导出选项：
  │     ├─ 导出范围: [当前任务 ▼] 或「全部任务」
  │     ├─ 脱敏级别: [无 ▼]
  │     │   ├─ none  → 原样导出
  │     │   ├─ mild  → 文件路径保留目录结构，文件名哈希；社区名脱敏
  │     │   └─ full  → 文件路径全部哈希；符号名类别化（"class_X"）；社区名脱敏
  │     └─ 描述: [________________]
  │
  ├─ 2. 导出管理器执行：
  │     ├─ 读取 export-meta.json 所需统计
  │     ├─ 从 main_db 查询 project / tasks / runs / reports
  │     ├─ 从 project_db 查询 source_files / graph_node / graph_edge / graph_doc / community_hierarchy / community_llm_results / report_subdocs / file_summaries / arch_snapshots / arch_snapshot_communities
  │     ├─ 如启用脱敏，对 file_path / name / summary 等进行脱敏处理
  │     ├─ 逐表流式写入 .jsonl（每行一个 JSON，避免全量加载）
  │     ├─ 写入 export-schema.sql
  │     └─ gzip 打包为 .topoexport
  │
  └─ 3. 返回文件路径 / 提供下载
```

### 4.3 流式写入策略

避免全量加载到内存——逐行从 SQLite 读取，逐行写入 `.jsonl`：

```python
import gzip, json, io

def _write_table_to_jsonl(db, table: str, f: io.TextIOBase):
    """流式读取表并逐行写入 JSONL"""
    cursor = db.conn.execute(f"SELECT * FROM {table}")
    while True:
        row = cursor.fetchone()
        if row is None:
            break
        d = dict(row)
        d["_table"] = table
        f.write(json.dumps(d, ensure_ascii=False) + "\n")
```

对于超大表（`graph_node`、`graph_edge`），使用 `fetchmany(5000)` 分块。

## 5. 导入流程

### 5.1 核心方法

```python
class ExportManager:

    def import_export(
        self, file_path: str,
        on_conflict: str = 'copy',       # 'copy' | 'skip'
    ) -> dict:
        """导入 .topoexport 文件，返回 {project_id, name, stats}"""
        pass
```

### 5.2 导入步骤

```
用户拖入 .topoexport 或 文件 > 导入
  │
  ├─ 1. 读取 export-meta.json（无需解压全部，仅读取压缩包头部）
  │     ├─ 检查 version <= MAX_EXPORT_VERSION
  │     └─ 显示项目名、统计、时间
  │
  ├─ 2. 用户确认导入选项：
  │     ├─ 项目名称: [自动取 export-meta 中的名称，可编辑]
  │     └─ 冲突处理: [⚪ 导入为副本  ⚪ 跳过已存在]
  │
  ├─ 3. 创建导入目录：
  │     ├─ ~/.topocode/imports/{project_name}_{timestamp}/
  │     └─ 目录内包含 .topocode/data/ 子目录结构
  │
  ├─ 4. 创建 project.db + 建表：
  │     ├─ 读取 export-schema.sql
  │     ├─ 在空 project.db 中执行建表 DDL
  │     └─ 创建必要索引
  │
  ├─ 5. 逐表流式导入：
  │     ├─ 解压 gzip 流式读取
  │     ├─ 每行 json.loads → INSERT OR IGNORE
  │     ├─ task_id 保持原值（UUID，冲突概率极低）
  │     └─ 每 5000 行 commit 一次
  │
  ├─ 6. 注册项目到主库：
  │     ├─ 在 projects 表插入记录
  │     ├─ root_path = 导入目录路径
  │     ├─ is_imported = 1
  │     ├─ has_file_changes = 0
  │     └─ file_count / language 从 stats 填充
  │
  ├─ 7. 在导入目录生成提示文件：
  │     README.txt：
  │     "该分析结果不包含源码。
  │      如需代码关联（符号跳转/行级定位），
  │      请将对应版本的源码解压到：{import_dir}/"
  │
  └─ 8. 前端进入项目报告页
```

### 5.3 ID 重映射策略

**不需要重映射**。理由：

- `task_id` 是原生 UUID，直接插入
- 导入为新项目（新 `project_id`），`task_id` 保持不变
- 引用关系（`graph_node.id → graph_edge.source_id`）在同一 `.topoexport` 内完整，导入后保持不变
- 与本地现有项目的 `task_id` 冲突概率极低（UUID），即使冲突也可以加后缀

## 6. 压缩率参考

### 6.1 为什么选择 JSONL + gzip 而不是直接打包 DB

| 指标 | 直接 cp project.db + gzip | VACUUM INTO + gzip | JSONL + gzip（选择） |
|------|--------------------------|-------------------|---------------------|
| 内部碎片 | ❌ 含空闲页 | ✅ 紧凑 | ✅ 无 |
| 索引开销 | ❌ 含全部索引（>30%） | ❌ 仍含索引 | ✅ 无索引纯数据 |
| 字段名重复损耗 | SQLite 二进制布局 | 同左 | ✅ 字段名高度重复 → DEFLATE 字典命中 |
| 基准（1k 文件 ~28MB 数据） | ~15MB | ~10MB | **~6-8MB** |
| 基准（10k 文件 ~270MB） | ~140MB | ~90MB | **~55-70MB** |

JSONL + gzip 压缩率最高，原因：
- 字段名（`"task_id":`、`"edge_type":`、`"comm_lv":`）在数万行中完全重复，DEFLATE 字典项几乎不占额外空间
- 没有 SQLite 页对齐（4KB 对齐导致跨页的相同内容无法合并）
- 没有索引数据结构（btree 页 + 页内指针不会随 gzip 压缩）

### 6.2 JSONL 的其他优点

- **流式**——导出和导入都不需要全量加载到内存
- **可演进**——未来加字段不影响旧版本导入
- **可局部加载**——如需按 task_id 过滤，流式判断即可
- **可调试**——解压后可直接查看内容，无需 SQLite 客户端

## 7. 脱敏选项

| 级别 | file_path | name / qualified_name | 社区名 | summary / content | 适用场景 |
|------|-----------|----------------------|--------|-------------------|----------|
| **none** | 原样 | 原样 | 原样 | 原样 | 内部团队分享 |
| **mild** | 保留目录结构，文件名 SHA256[:8] | 原样 | 脱敏为 "社区_1" | 保留 | 对外展示，保护源文件名 |
| **full** | 全部 SHA256[:8] | 类别保留（"class_1"、"func_2"） | 全部脱敏 | 可选保留 | 公开基准测试 / 匿名上传 |

脱敏在导出时执行，不影响源库数据。

## 8. 与云端服务的区别

| 维度 | 本地导出 .topoexport | 云端匿名上传（已存在） |
|------|---------------------|----------------------|
| 数据内容 | **完整分析结果**（节点/边/摘要全部） | **仅脱敏统计**（社区数、节点数、质量评分） |
| 可还原状态 | ✅ 导入后完整可查 | ❌ 不可还原 |
| 文件路径 | 保留或脱敏可选 | 不包含 |
| 符号名 | 保留或脱敏可选 | 不包含 |
| 代码内容 | 不包含 | 不包含 |
| 用途 | 用户间分享 | 产品匿名数据收集 |

两者互补——本地导出用于团队协作，云端上传用于产品优化。

## 11. 与 Web AI 会话的关系

导入后的项目数据可以直接作为 Web AI 会话的上下文源。用户可打开 Web AI 助手，选择导入的项目，基于其中的社区/符号数据进行分析。

- 社区图引用（`?ref=graph:...`）对导入项目同样有效
- AI 工具调用（`topocode_community`、`search_symbols` 等）在导入项目上正常工作
- 由于无源码，`get_file_content` 工具会返回「该分析结果不含源码」提示
